## Core concepts (revision)

### Docker

- **Image** = immutable packaged app + deps. **Container** = running instance.
- **Dockerfile → build → Image → run → Container → push → Registry → pull.**
- **Layers:** each instruction is a cached layer. Copy `requirements.txt`
  *before* source code so dependency installs are reused.
- **Multi-stage build:** builder stage makes wheels; runtime stage installs
  them — no build tools in the final image.
- **`.dockerignore`:** keeps secrets (`.env`), `.git`, caches out of the
  build context.
- **Non-root user** (`USER app`) reduces blast radius if the app is compromised.
- Containers share the host kernel — lighter than VMs but NOT automatically
  a strong security boundary.

### Git / GitHub Flow

`main` is protected. Feature branch → commit → push → **Pull Request** →
automated CI → review → merge → deploy.

### CI/CD

- **CI (Continuous Integration):** every push/PR is automatically linted,
  tested, and built. Failures block the merge.
- **CD — Continuous Delivery:** releases are always deployable; a human may
  approve the final deploy. **Continuous Deployment:** every green build
  deploys automatically.
- GitHub Actions vocabulary: **workflow** (file) → **job** → **step** →
  **action** (reusable unit). Runs on a **runner** (VM).
- **Cache** speeds up future runs; **artifact** preserves a build output.
- Advanced: `matrix` builds, `needs:` job dependencies, `concurrency`,
  environments with approval gates, reusable workflows, cron schedules.

### Registries: tag vs digest

- **Tag** (`ml-api:v1.0.0`, `:latest`) is movable — deploy by it and you may
  get different content later.
- **Digest** (`ml-api@sha256:...`) is immutable — use it for production deploys
  and rollbacks. The deploy workflow does exactly this.
- Registries: Docker Hub, GHCR (`ghcr.io`), Google Artifact Registry.

### Cloud Run contract

1. Listen on `0.0.0.0` (not `127.0.0.1`).
2. Listen on `$PORT` (Cloud Run injects it, default 8080).
3. Cloud Run creates immutable **revisions** per deploy.

### OIDC + Workload Identity Federation (key security concept)

GitHub Actions gets a **short-lived OIDC token**; Google verifies it comes
from your trusted repo/branch and exchanges it for temporary cloud access.
**No long-lived service-account JSON key stored in GitHub Secrets.**
Setup: workload identity pool → OIDC provider (restricted by
`attribute-condition` to `OWNER/REPO` + `refs/heads/main`) → deployer service
account with minimal IAM (Artifact Registry Writer, Cloud Run Developer,
Service Account User).

### Supply chain & production engineering

- **SBOM** = software bill of materials (dependency inventory).
- **Provenance** = evidence of how/where the image was built.
- Both generated by `docker/build-push-action` (`sbom: true`, `provenance: true`).
- Scan images with **Trivy**; pin actions to SHAs for hardened pipelines.
- Secrets: runtime secrets via **Secret Manager**, never `ENV` in the image,
  never committed to git.
- **Model registry ≠ container registry:** MLflow versions models;
  Artifact Registry versions images that contain them.

### Deployment strategies

- **Blue-green:** two full environments, switch traffic at once.
- **Canary:** shift a small % of traffic to the new revision, watch metrics,
  then ramp up. Cloud Run: `gcloud run services update-traffic ... --to-revisions`.
- **Rollback** = point traffic back to the previous revision.

### Observability — three pillars

- **Logs** (what happened), **Metrics** (how much/how fast), **Traces** (where
  time went). For ML also watch **data drift / prediction drift**, not just
  infra health — a service can be "healthy" while its predictions degrade.

### Scaling & cost

- Vertical = bigger instance; horizontal = more instances (Cloud Run does this
  automatically up to `--max`).
- Watch: CPU/memory, concurrency, min instances (cold starts!), request
  timeout, startup/liveness probes. Set budget alerts.

## Interview questions — quick answers

1. **Docker?** Packages app + runtime deps into a portable image so "works on
   my machine" problems disappear.
2. **Image vs container?** Image = recipe/artifact; container = running copy.
3. **Container vs VM?** VM virtualizes hardware + guest OS; container is an
   isolated process sharing the host kernel — lighter, faster.
4. **Layers?** Each Dockerfile instruction produces a cached, reusable layer.
5. **Why caching matters?** Unchanged layers (e.g. pip install) are reused,
   making rebuilds fast — order instructions from least→most frequently changed.
6. **Multi-stage build?** Separate build deps from runtime; copy only what's
   needed → smaller, more secure image.
7. **`.dockerignore`?** Excludes files from the build context (secrets, caches).
8. **Non-root?** Limits damage if the app is compromised; good security practice.
9. **Compose?** YAML-defined multi-container apps for local dev — not a
   production orchestrator.
10. **Volume vs bind mount?** Volume = Docker-managed persistent storage;
    bind mount = direct host directory mapping.
11. **Registry?** Stores/distributes images (Docker Hub, GHCR, Artifact Registry).
12. **Tag vs digest?** Tag = movable name; digest = immutable content ID.
13. **CI?** Automatically integrate + test every change.
14. **Delivery vs Deployment?** Delivery = always releasable, human gate;
    Deployment = auto-deploy on green.
15. **Runner?** The VM that executes a workflow job.
16. **Workflow/job/step/action?** Workflow = file; job = task group; step =
    one operation; action = reusable automation unit.
17. **Cache vs artifact?** Cache = speed up future runs; artifact = preserved
    output you can download/pass between jobs.
18. **Secrets vs Environments?** Secrets = encrypted values; environments =
    deployment targets with protection rules/approval gates.
19. **OIDC?** OpenID Connect — one IdP vouches for identity to another.
20. **WIF safer than keys?** No long-lived credential to leak/rotate; tokens
    are short-lived and scoped to trusted repo+branch.
21. **Artifact Registry?** Google Cloud's managed container image repository.
22. **Cloud Run revision?** Immutable versioned deployment of a service.
23. **Canary?** Gradual traffic shift to new version (e.g. 5%→100%).
24. **Blue-green?** Two full stacks; instant traffic switch after validation.
25. **SBOM?** Inventory of all components/dependencies in an artifact.
26. **Provenance?** Signed evidence of how/where the artifact was built.
27. **IaC?** Defining infrastructure in code (Terraform etc.) for repeatability.
28. **GitOps?** Git is the source of truth; agents reconcile cluster state to it.
29. **Logs/metrics/traces?** What happened / how much & how fast / where time went.
30. **Data drift?** Input feature distribution shifting vs training data →
    model predictions degrade even while infra looks healthy.

## Commands cheat sheet

```bash
# local
docker build -t ml-inference-api:v1 .
docker run -d --name ml-api -p 8000:8080 ml-inference-api:v1
docker compose up --build -d

# gcloud (one-time)
gcloud auth login
gcloud config set project PROJECT_ID
gcloud services enable run.googleapis.com artifactregistry.googleapis.com \
  iam.googleapis.com iamcredentials.googleapis.com sts.googleapis.com
gcloud artifacts repositories create ml-containers \
  --repository-format=docker --location=asia-south1
gcloud auth configure-docker asia-south1-docker.pkg.dev

# manual image push
docker build -t asia-south1-docker.pkg.dev/PROJECT/ml-containers/ml-api:v1 .
docker push asia-south1-docker.pkg.dev/PROJECT/ml-containers/ml-api:v1

# manual deploy
gcloud run deploy ml-inference-api \
  --image asia-south1-docker.pkg.dev/PROJECT/ml-containers/ml-api:v1 \
  --region asia-south1 --port 8080 --memory 1Gi --cpu 1 --max 5 \
  --allow-unauthenticated

# traffic / rollback
gcloud run services update-traffic ml-inference-api --region asia-south1 \
  --to-revisions OLD=95,NEW=5
```
